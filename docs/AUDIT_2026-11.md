# Audit, November 2026

Read from the code and the repository only. Nothing here was run on a phone or against the live Supabase project (it is paused).
**Fixed** = changed in this round. **Open** = needs a decision, a phone, or access I do not have.

## 1. AI-generated code and security
Scanned all Kotlin and workflow files for the usual mistakes of generated code.
- SQL built from text: none reaches user input. The few `execSQL`/`rawExecSQL` strings contain only app-made paths, a hex key, table and column names, or fixed sub-queries. Room `@Query`s use parameters.
- Weak crypto, WebView, shell commands, hard-coded secrets, secrets in logs: none found. (`Math.random` is only retry jitter; "pin" in drawer logs is the printer's drawer pin, not a user PIN.)
- Untrusted input (SMS, QR, sync, webhook) already goes through the validators named in CLAUDE.md.
- **Open (low):** GitHub Actions are pinned by tag (`@v7`), not by commit. The release workflow, which holds the signing secrets, uses a third-party action (`softprops/action-gh-release@v3`). Pinning it to a commit SHA removes the risk of a moved tag. Dependabot already proposes action updates monthly.

## 2. Database at rest: SQLCipher vs Android file encryption (FBE)
- FBE protects files while the phone is locked and is always on for Android 10+. It does nothing once the phone is unlocked and the app runs, nor for files copied out by USB, a backup, or a file manager.
- SQLCipher (AES-256, key kept in the Android Keystore) protects the database file itself in those cases, so both layers are worth keeping. Neither protects against someone who can unlock the phone and open the app, or a rooted phone running the app's own process.
- What the code does right: random 32-byte key never replaced if unreadable; conversion to a new file, verified before the swap; plain copy of the old database deleted after 3 days; cloud backup limited to settings; auto backups stay in private storage.
- **Fixed:** the end-of-day backup made a file with no passphrase and said only "Backup saved". It now says it has no passphrase and points to Settings > Data & Backup for a protected copy.
- **Open (medium):** manual and end-of-day backups without a passphrase are plain copies in the app's external folder (reachable over USB). Consider making the passphrase required for every backup.
- **Open (low):** the Keystore key is not StrongBox-backed and not tied to an unlocked screen. Unlock-required would break background sync and the daily report, so leave it; StrongBox could be requested with a fallback.
- **Open (low):** the 3-day plain safety copy after the first encryption is a deliberate trade-off against a bad conversion.

## 3. Google Play compliance and permissions
The app is distributed by GitHub today. Publishing on Google Play would hit these:
- **Blocker: target API level.** Play requires new apps and updates to target Android 16 (API 36) since 31 August 2026. The app targets 35 (compile 37). Raising it changes behaviour (large-screen orientation and resizing rules, predictive back) and needs a test on real phones, including a tablet till.
- **Blocker: `RECEIVE_SMS`.** Play allows it only for a default SMS, phone or assistant app (or a granted exception). Reading M-Pesa messages to confirm payments does not qualify. The alternatives are the Daraja prompt (already built) or entering the SMS code by hand.
- **Blocker: `REQUEST_INSTALL_PACKAGES`.** Needs a declaration, and Play forbids apps from updating themselves outside Play, so the in-app updater must be absent from a Play build.
- **Review: `READ_CONTACTS`** (customer picker) needs a declaration and a Data safety entry; `CAMERA`, notifications and Bluetooth are normal for the purpose.
- Good already: no cleartext traffic, receiver guarded by `BROADCAST_SMS`, backup rules limited, optional hardware marked `required="false"`.
- **Suggested path:** a separate "play" build without SMS, installer and updater, with a Data safety form. This needs its own release workflow, so it was not started.

## 4. Hardware fragmentation and Bluetooth
- Permissions already switch by Android version (`BLUETOOTH_CONNECT` on 12+, legacy below), and missing permission is handled without a crash.
- **Fixed:** connecting to the printer could hang for a long time on a printer that is off or out of range. Each attempt now stops after 10 seconds. If the normal secure link fails, the "insecure" link kind many cheap printers need is tried before giving up.
- **Open:** no automatic retry after a print fails mid-receipt on a flaky link; very cheap printers may need data in smaller pieces with short pauses. Needs real printers to tune.
- **Open:** Arabic on thermal printers (needs a printer with an Arabic code page) is untested on hardware.

## 5. Offline sync conflict resolution
- Sync carries sales and later refunds/voids. Prices, stock and customers always come from the main phone, so the field-by-field "newest edit wins" rules in `ConflictMerge` are tested but **not used by the app yet**. The code comment describes more than the app does.
- Good: sales are applied once (duplicates ignored), stock never goes below zero, a sale refunded on one till and voided on another is applied once and flagged, a refused till sale now notifies the main phone's owner.
- **Open (low):** because stock is clamped at zero when a sale is applied, a later refund of that sale adds back the full quantity, so stock can end up higher than reality. A shop would see it in a stock count.
- **Open (low):** a till's refund can be refused if the sale it refers to was itself refused ("was never received"); both stay in the conflict list.
- **Open:** needs two real phones to test end to end.

## 6. Supabase RLS edge cases
Review of `cloud/*.sql` (the live project is paused, so policies set by hand there were not seen).
- Checked and fine: tables have RLS and no direct grants; the secret and link codes are stored hashed; codes expire and can be used once; failed attempts do not burn a code; wrong store and wrong secret give the same answer and delay; owner deletion cascades.
- **Fixed:** the public functions now refuse secrets over 200 characters and snapshots that are not JSON objects before doing any work.
- **Open (medium):** a wrong guess costs the database a 1.5 s wait; with the public key anyone can tie up connections. Use Supabase rate limits; keep "Confirm email" on with a sign-up limit.
- **Open (low):** an old phone restored from a backup can overwrite a newer snapshot (no version check). Harmless to other owners, but the dashboard may show older numbers until the next push.
- **Open (low):** each account can store up to 25 shops of 400 KB each; many accounts could still fill storage, so the sign-up limit matters.
